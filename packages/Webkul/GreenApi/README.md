# GREEN-API для Krayin CRM

Пакет добавляет WhatsApp-раздел, привязку разговора к существующему контакту/сделке, текстовые исходящие сообщения, приём входящих сообщений и файлов (метаданные и ссылка), синхронизацию статусов и режимы управления диалогом.

## Установка в этом форке

Поддерживается Krayin 2.2, PHP 8.3+, Laravel 12, MySQL/MariaDB.
Регистрация находится в двух точках приложения: PSR-4 в корневом composer.json и provider в bootstrap/providers.php. Контроллеры, таблицы, маршруты, шаблоны, разрешения и переводы находятся внутри этого пакета.

1. Установите зависимости приложения: `composer install`.
2. Настройте базу данных Krayin и выполните обычную установку CRM.
3. Для уже установленной CRM выполните `php artisan migrate --force`.
4. Добавьте параметры ниже в окружение сервера, затем выполните `php artisan config:cache`.
5. В роли оператора включите WhatsApp: раздел, просмотр, отправку и управление диалогом. Настройки подключения выдавайте администраторам.
6. Проверьте соединение в `/<APP_ADMIN_PATH>/green-api/settings`. Ожидаемое состояние авторизованного стандартного инстанса — `authorized`.

Пакет по умолчанию выключен. Данные реального инстанса и токены в репозитории отсутствуют.

## Обновление Krayin

База интеграции — upstream `krayin/laravel-crm`, ветка `2.2`, коммит `64ef70505c5d4320231420bb21adf99dd1698e4e`.
Сохраняйте `origin` на своём форке, а `upstream` — на исходном репозитории. После слияния этого PR обновления можно получать через `git fetch upstream` и `git merge upstream/2.2` в основной ветке форка.
За пределами пакета нужны только его PSR-4-регистрация и service provider; изменения модулей Admin, Contact и Lead не требуются. При конфликте в `composer.json` или `bootstrap/providers.php` сохраняйте обе регистрации. Перед обновлением рабочей CRM сделайте резервную копию БД, проверьте слияние и тесты на тестовом окружении, затем выполните миграции.

## Окружение

```dotenv
GREEN_API_ENABLED=true
# Используйте apiUrl именно из своего кабинета GREEN-API.
GREEN_API_URL=https://api.green-api.com
GREEN_API_INSTANCE_ID=
GREEN_API_TOKEN=
# Отдельный случайный секрет, минимум 32 символа. Не используйте API token.
GREEN_API_WEBHOOK_TOKEN=
# Необязательный ответственный для новых неизвестных разговоров.
GREEN_API_DEFAULT_USER_ID=
GREEN_API_QUEUE=default
QUEUE_CONNECTION=database
```

Секрет вебхука можно создать локально: `php -r 'echo bin2hex(random_bytes(32)), PHP_EOL;'`.
Секреты вводятся в окружении сервера, не через поля карточки CRM. На странице настроек токены не отображаются. Не включайте в production логи HTTP-клиента с URL: GREEN-API передаёт API token в пути запроса.

Разрешены HTTPS API-адреса доменов `green-api.com` и `greenapi.com`, включая поддомены. Перенаправления отключены.

## Вебхук и очередь

В кабинете стандартного GREEN-API настройте:

- Webhook URL: `https://<crm-domain>/green-api/webhook` (без префикса admin).
- Webhook URL Token: значение `GREEN_API_WEBHOOK_TOKEN`; сервер проверяет заголовок `Authorization: Bearer <token>`.
- `incomingWebhook=yes` — входящие сообщения.
- `outgoingMessageWebhook=yes` — сообщения, отправленные с телефона.
- `outgoingAPIMessageWebhook=yes` — эхо отправки через API.
- `outgoingWebhook=yes` — статусы доставки.

Пакет не перезаписывает настройки инстанса автоматически: настройка нового Webhook URL заменит предыдущего получателя.

Для очереди database создайте стандартные таблицы очереди Laravel, если их ещё нет:
`php artisan make:queue-table`, `php artisan make:queue-failed-table`, затем `php artisan migrate --force`.
Если таблицы уже существуют, повторно команды генерации не нужны.
Запускайте постоянно под supervisor/systemd:
`php artisan queue:work database --queue=default --tries=5 --timeout=60`.

Полученный вебхук сначала записывается в БД, затем обрабатывается заданием очереди. Повторный вебхук не создаёт повторное сообщение. Неудачно обработанные задания проверяйте через `php artisan queue:failed` и повторяйте `php artisan queue:retry <id>`.
Если отправка задания в очередь завершилась ошибкой, обработчик отвечает ошибкой; повторная доставка вебхука поставит сохранённое событие в очередь заново.

## Работа оператора

- В карточке сделки выберите номер контакта и нажмите WhatsApp. Это открывает/привязывает диалог, но не отправляет сообщение.
- Номер должен быть международным. Пакет удаляет пробелы, скобки и дефисы, но не угадывает код страны.
- Входящий номер привязывается к контакту только при единственном совпадении. При нескольких совпадениях диалог остаётся непривязанным.
- Неизвестные диалоги без ответственного доступны пользователям с глобальной областью просмотра.
- Если неизвестный диалог появился раньше контакта, пользователь с глобальной областью просмотра должен открыть WhatsApp из соответствующей сделки: это привяжет диалог и назначит ответственного сделки. Операторы с индивидуальной областью не могут самостоятельно забирать неизвестную историю.
- При отправке оператором или с телефона режим становится «Человек».
- «Пауза» отключает будущую автоматизацию, но допускает ручной ответ. «Остановлен» и отказ от сообщений блокируют отправку.
- Сообщения в истории показаны от новых к старым, по 50 на страницу. Для обновления есть кнопка.
- Статус sent означает принятие провайдером. delivered/read приходят отдельными вебхуками.
- Текст до 20 000 символов, включая emoji, сохраняется без обрезки; исходящий JSON передаёт Unicode без раздувания escape-последовательностями.
- Статусы ошибок провайдера (`failed`, `noAccount`, `suspended`, устаревший `yellowCard`, `notInGroup`) отображаются как ошибка отправки. Подтверждённые delivered/read не понижаются задержанными ошибками; ранние статусы учитываются и для сообщений с телефона.
- Вебхуки с телефона не снимают установленную оператором остановку или отказ от сообщений.
- При таймауте или неясном ответе отправка получает unknown. Автоматически она не повторяется: прежде чем отправлять заново, проверьте телефон/журнал провайдера.
- Повтор одного HTTP-запроса с тем же `client_reference` UUID возвращает сохранённый результат. Другой текст с тем же UUID отклоняется.
- Собственные API-эхо сохраняются как события, но не дублируют исходящие сообщения. Исходящие другого приложения, использующего тот же инстанс, пока не импортируются в переписку.

Права на действие и область видимости проверяются на сервере. История, отправка и изменение режима недоступны для чужого диалога. Связанные контакт и сделка также должны находиться в области доступа оператора.

## Точки расширения для двух ботов

После сохранения нового входящего сообщения Laravel публикует событие:
`green-api.message.received` с аргументами `messageId`, `conversationId`.

Сборщик базы создаёт организации, контакты и лиды через API CRM. ИИ-продажник подключается отдельным пакетом/сервисом. Это изменение не содержит самого ИИ-продажника, API-доступа n8n к переписке или автоматической рассылки.
Режим «Бот» сейчас хранит состояние для будущего обработчика. Будущий бот должен перед каждой отправкой атомарно проверять режим, отказ и актуальность входящего сообщения; ручные контроллеры этого пакета всегда являются действиями человека.

## Границы первой версии

- Один стандартный GREEN-API WhatsApp-инстанс на установку. WABA-адаптер не реализован.
- Исходящие — текст. Приём медиа сохраняет подпись, имя и HTTPS-ссылку, не скачивая файл автоматически. Ссылки провайдера могут истекать.
- Групповые чаты, реакции и редактирование/удаление старых сообщений не синхронизируются.
- Настройки токенов — в серверном окружении, отдельного редактора секретов в интерфейсе нет.
- Поиск контакта при первом открытии чата проходит по номерам CRM; при большой базе потребуется индекс нормализованных номеров.
- Нужны резервное копирование БД, контроль failed jobs и принятая вами политика хранения переписки/исходных webhook events. Они хранятся до удаления администратором.
